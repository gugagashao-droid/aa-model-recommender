# 模型推荐输出规范

## 版本选择

- **原子任务** → 用"单模块版式"(第一节)。
- **宽泛任务**(已拆解)→ 用"多模块版式"(第二节),并附第三节的跨模块综合建议。

## 一、单模块版式(原子任务)

按此顺序输出:

1. **一句话结论**:首选模型 + 一句为什么(基于哪个子榜第几名)。
2. **依据说明**:用了哪些子榜(AA 榜或外部榜)、数据日期、来源链接;说明反问得到的场景/优先级如何影响选择;如做过反问,简述"根据你的回答(…)"。来源要标清:"官方"、"聚合站转载(口径源自 AA)"或"外部榜(置信度:中/高)"。
3. **Top3 对比表**:用第四节字段表。
4. **逐条推荐理由**:每个模型 2–4 句。
5. **可靠性提示**:自报/证据等级、变体配置、数据较旧等。

## 二、多模块版式(宽泛任务,核心)

宽泛任务**必须逐模块给推荐**,不能给一个笼统答案。按此顺序输出:

1. **需求细化复述**:1–2 句复述反问得到的关键背景(如"本科、计算机专业、做 Web 后台、强调设计"),让用户看到反问被采纳;列出采用的假设。
2. **任务拆解总览表**:列出所有叶子模块及每个模块的核心能力与选用子榜,让用户一眼看到拆成了哪些块。

   | 模块 | 核心能力 | 依据子榜 |
   |---|---|---|
   | 例:前端-UI 审美 | 模型生成好看的页面 | Contra Frontier Design(外部榜) |
   | 例:后端-代码评审 | 合并判定/质量 | `aa_frontiercode_20` |

3. **逐模块 Top3 推荐**:对每个叶子模块单独输出一小节,包含该模块的 Top3 对比表(第四节字段)+ 该模块首选模型的一句话理由。理由必须绑定该模块所用子榜的真实名次/分数,并针对该模块能力(如"UI 审美模块看 Contra Frontier Design 的 Elo","review 模块看 FrontierCode 的合并判定表现(代理榜单)")。
4. **跨模块综合建议**:见第三节。

> 模块较多时,总览表保留全部模块,逐模块详情可按重要性排序;每个模块至少给出首选模型,Top3 对比表可只对重点模块完整展开,其余用一行"首选 / 备选"表示,避免输出过长。

**三条硬规则:**

- **共用同一子榜的模块合并成一张表。** 例如前端开发、视觉还原、代码评审都落在同一榜上,就写一张表,标题写"前端开发 / 视觉还原 / 代码评审(共用 X 榜)",不要重复三份。
- **代理榜单必须说明。** 总览表"依据子榜"列里,代理榜单后面加"(代理)",并在该模块首选理由里写一句"该榜不直接衡量本能力"。
- **榜上的人类对照组、匿名隐藏模型、已下线模型不进 Top3**,在备注里提一句即可。

## 三、跨模块综合建议(宽泛任务必含)

- **通用强模型**:是否存在一个模型在多数模块都排靠前,可承担主线;点名并说明覆盖哪些模块。
- **专用模型**:哪些模块必须用专用模型(如配图素材用出图模型、SRE 用运维强模型),给出该模块首选。UI 页面设计看设计榜(Contra Frontier Design),它评的是能生成页面的模型,不是出图模型。
- **组合策略**:给出"主模型 + 几个模块替换模型"的可执行组合建议。
- **取舍**:结合优先级说明成本/效果/速度的取舍。

## 四、Top3 对比表字段(两种版式通用)

| 列 | 说明 |
|---|---|
| 排名 | 该模块综合排序后的 1/2/3(不是单个子榜名次) |
| 模型(配置) | 模型名 + effort 配置,如 Claude Opus 5.5 (max) |
| 厂商 | Anthropic / OpenAI / Google 等 |
| 子榜名次 | 在所选子榜上的原始名次与分数,如 "#1 · 64.6" 或 "Elo 1815" |
| 输出价 $/1M | 抓到则填,否则填 "—" |
| 速度/时延 | 抓到则填(tok/s 或每任务分钟),否则填 "—" |
| 权重/部署 | 开源权重 / 闭源 / 受限,抓到则填 |
| 一句话点评 | 该模型相对本模块能力的关键优势或短板 |

## 五、推荐理由写法

- **绑定榜单事实**:"在 Image Arena 上以 Elo X 排第 1""在 AA-Briefcase v1.1 上 Elo 1815 排第 1",不要空泛说"能力强"。
- **针对本模块/场景**:说清为什么适合这个具体模块(写代码 vs 做设计 vs 做 review 关注点不同)。
- **结合优先级与部署**:成本优先点性价比,速度优先点时延;要开源本地则标注是否满足。
- **区分独立测评 vs 自报**,不把自报第一当绝对结论。

## 六、措辞与稳定性

- 用中文,简洁直接,避免营销腔与绝对化("最强""唯一");改成"在本模块/场景下、按该榜数据,排在最前"。
- 所有分数/名次必须来自本次实时抓取,不得凭训练记忆编造模型名或分数。
- 排名只反映所测子榜,不等于真实生产表现,结尾提醒"建议在自己的任务上小样本验证"。
- 无价格/速度数据如实留 "—",不要臆造。榜页没写数据日期的,写"页面未标日期"。
- **成本优先的口径要写明**:先写出质量下限(用户给定,或"取该榜前三分之一"的假设)。分数类榜写"分数÷实际成本"或"分数÷输出价(未计输入价与思考 token,仅为粗估)";Elo 类榜写"达标候选里按价格升序,并列出与榜首的 Elo 差距",不出现"Elo÷价格"。
- **外部榜、聚合站、镜像数据要带标注**:来源写成"官方"、"聚合站转载(口径源自 AA)"、"镜像(来源 X,同步日期 Y)"或"用户提供"之一;中置信的来源在表下方写明局限(如"单一来源""裁判未披露""票数未披露");分差落在置信区间内的名次,写"并列/接近",不硬排先后。Contra 这类按维护者指定为高置信的榜,仍要写出样本量(33 份简报)。
- **写作类模块要写明语言**:外部写作榜以英文为主(aiwritingbenchmark 没有中文版)。中文写作用 LM Arena 中文类别;其他语言或该榜没覆盖的,注明"榜单语言与任务语言不一致,需自测"。
- **没有达标榜的能力**(如润色)直接写"无达标公开榜",给小样本自测建议,不留空表。
- **降级与置信度披露**:若某模块走了 `fetch-guide.md` 第四节情形 B(自检 SKILL 清单 / 外部榜),必须在该模块输出中写明触发了哪一级降级、结论来自哪类来源、置信度等级(高/中/低)及其局限;若最终找不到合格榜单,明确告知"该维度无达到置信门槛的公开榜单"并给保守建议,绝不拼凑看似精确的 Top3。
- 一旦为 SKILL 补收录了漏掉的榜单(如 Arena 类),在输出中顺带提一句"该榜已补入技能清单",让用户知道自检真的产生了改进。
